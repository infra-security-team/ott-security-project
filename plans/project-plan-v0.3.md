## 04. 실제 장비는 각자의 PC에서 실행합니다

보고서의 전체 구성도는 한 회사처럼 연결해 표현하지만, 실제 실습은 팀원별 PC 5대로 나누어 진행합니다.

- M1 본사: 교실망 ↔ VyOS1 ↔ UTM1 ↔ GNS3 VLAN·기존 본사 장비
- M2 관제: 교실망 ↔ VyOS2 ↔ UTM2 ↔ 관제·시험·관리 VMnet
- M3 서비스: 교실망 ↔ VyOS3 ↔ UTM3 ↔ 진입 서버·앱·DB·개선 후 관리 VMnet
- M4 백업: 교실망 ↔ UTM4 ↔ 백업·복제 구역 (교실망 직접 연결은 제안)
- M5 캐나다: 교실망 ↔ UTM5 ↔ 운영·콘텐츠·관리 VMnet (교실망 직접 연결은 제안)

각 행은 서로 다른 물리 PC 안에서 실행합니다. UTM 번호는 담당 번호와 같습니다. VMnet은 같은 PC 안의 가상 연결이며, 팀원 간 연결은 교실 물리망을 통과합니다.

VPN 계획은 M1–M5(캐나다 업무), M1–M4(관리·관제), M3–M4(DB 백업·복제)입니다. 연결선은 계획이며 실제 개통 완료를 뜻하지 않습니다.

Bridged(브리지)는 가상 장비의 네트워크 카드를 교실 물리망에 연결하는 방식입니다. PC 사이 통신은 실제 시험이 필요합니다.

## 05. M1 | 본사 장비를 보존하고 VLAN을 구성합니다

담당 유용수 / 본사 네트워크와 업무망 VPN의 중심 연결을 담당합니다. 기존 장비를 유지합니다.

| 구역 | 보존할 장비·역할 | 구축할 내용 |
| --- | --- | --- |
| 외부 공개 구역 | WEB·DNS·SFTP 서버 3대 | 본사 UTM의 전용 내부 포트에 연결합니다. |
| 사내 서버 구역 | WAS·DB·Backup·Log·NFS 서버 5대 | 사내 서버 통신과 필요한 접근 권한을 설정합니다. |
| 직원·공통 구역 | 마케팅·인사·영업 PC 각 2대 / Samba·DHCP 서버 2대 | GNS3에서 부서별 VLAN을 구성합니다. 공통 서비스의 사용 범위를 정합니다. |
| 관리 구역 | 관리 PC 2대 / 기존 가상 스위치 총 10대 유지 | 관리 구역은 전용 포트, 직원·공통 구역은 VLAN 전달용 연결을 사용합니다. |
| 연결·보안 시험 | M1–M5 및 M1–M4 VPN / 시나리오 1 | 직원 PC의 불필요한 관리 접속을 막고 승인된 관리자 접속을 확인합니다. |

전체 합계: 서버 10대·직원 PC 6대·관리 PC 2대·스위치 10대. 상세 배선은 토폴로지 v1.1을 따르며, 동시 실행 수는 메모리 사용량으로 조절합니다.

## 06. M2·M3 | UTM 포트마다 별도 가상망을 연결합니다

UTM은 방화벽·VPN 등 경계 보안 기능을 제공하는 장비입니다. NIC는 네트워크 카드, VMnet은 VMware 내부 가상망입니다.

| 담당 | 구축할 구성 | 확인할 결과 |
| --- | --- | --- |
| M2 윤서영<br>보안 관제 | 외부·관제·시험·관리용 NIC 총 4개. 각 내부 구역은 별도 VMnet에 직접 연결합니다. | VLAN과 UTM 바로 아래 통합 스위치를 사용하지 않습니다. |
| M2 수집·관리 | Wazuh로 서버 로그를 모으고 Suricata로 관측 가능한 패킷을 분석합니다. | 반복 SSH 로그인 실패를 탐지합니다. 패킷 복사 수집 가능 여부는 별도 확인합니다. |
| M3 홍은서·PL<br>서비스 인프라 | 외부·진입 서버·앱·DB 구역을 포트별 VMnet으로 분리합니다. 개선 후 관리 구역을 추가하면 NIC 총 5개입니다. | Nginx가 웹 요청을 받아 Spring으로 전달하고 MySQL과 연동합니다. |
| M3 가상화·배포 | vSphere는 VM 운영, Docker는 앱 이미지 제작, Kubernetes는 앱 컨테이너 배치·복구에 사용합니다. | 제어 노드 1대·실행 노드 2대를 목표로 32GB 자원과 중첩 가상화 가능 여부를 확인합니다. |
| 공동 작업 | M5가 제공한 코드를 M3가 배포합니다. M2는 로그 수집을 지원합니다. | M2는 시나리오 2, M3는 시나리오 3을 시험합니다. |

SSH는 서버 원격 관리 접속입니다. M3의 React 화면·영상·자막은 AWS S3와 CloudFront에, 한국 서비스망에는 API와 DB를 배치합니다.

## 07. M4·M5 | 복구와 캐나다 업무·서비스를 맡습니다

백업·복구, 캐나다 사내 업무, 고객용 OTT·Store의 역할을 구분하여 진행합니다.

| 담당 | 주요 작업 | 협업·완료 기준 |
| --- | --- | --- |
| M4 박진혁<br>백업·복구 | M3의 DB를 백업하고 개선 후 복제 DB를 구성합니다. S3에 백업 사본을 보관합니다. | M3와 DB 버전·계정·데이터를 맞추고 별도 DB와 AWS EC2에서 복원을 시험합니다. |
| M4 연결·시험 | M3–M4 VPN은 DB 백업·복제, M1–M4 VPN은 본사 경유 관리·관제에 사용합니다. | 비인가 계정의 백업 파일 읽기를 시험하는 시나리오 4를 수행합니다. |
| M5 유은혜·PM<br>캐나다 사내망 | UTM의 외부·운영부서·콘텐츠부서·관리용 NIC 총 4개를 사용합니다. VLAN 없이 VMnet으로 분리합니다. | M1–M5 VPN으로 본사 업무를 연결하고, 한국 시험 DB 직접 접근을 제한하는 시나리오 5를 수행합니다. |
| M5 코드·AWS | React·Spring·FastAPI·AI 자막·Store 코드를 개발하고 AWS를 구성합니다. | M3에 실행 방법·DB 구조·앱 이미지를 전달합니다. M3는 한국 배포와 DB 운영을 맡습니다. |
| M5 일정 관리 | 팀 작업·막힌 문제·결정 사항을 취합합니다. | 10/23 Store의 예상 작업량·비용을 검토합니다. 일정 변경은 팀에서 결정합니다. |

M4·M5의 UTM을 교실망에 직접 연결하는 인터넷 출구는 제안입니다. 실제 연결 방식은 10/23까지 확인합니다.

## 08. React·영상·자막은 AWS, API는 한국 서비스망

파일은 S3에 올리고 CloudFront로 제공합니다. 브라우저는 화면·영상 요청과 로그인·목록 API 요청을 따로 보냅니다.

1. **배포·업로드:** M5가 React 화면 파일·MP4 영상·VTT 자막을 비공개 S3에 올립니다. 서울 리전을 기준안으로 검토합니다. VTT는 브라우저가 표시하는 자막 파일입니다.
2. **화면·영상 요청:** 브라우저 → CloudFront → 필요 시 S3 원본 조회. S3 원본 읽기 제한(OAC)을 적용합니다. 로그인 전용 영상의 시청 권한은 별도 설정·시험합니다.
3. **API 요청:** 브라우저 → 공개 HTTPS 진입점(가능 여부 확인 전) → M3 Nginx → Kubernetes의 Spring → MySQL. API는 로그인·목록 같은 데이터 요청입니다. HTTPS 인증서와 브라우저의 다른 출처 요청 허용(CORS)을 확인합니다.
4. **자막 생성:** Spring → FastAPI → 음성 인식(STT)·한영 번역 → VTT 생성 → S3 업로드 → DB에 자막 URL·처리 상태 저장. DB에는 영상 원본 대신 제목·파일 주소 등 정보를 보관합니다.
5. **별도 Store:** OTT 링크 → 캐나다 ALB → EKS의 React·Spring → 비공개 RDS. 한국 OTT DB와 분리하며 고객은 사내 VPN을 사용하지 않습니다.

CDN은 파일을 사용자에게 전달하는 배포망입니다. 캐나다 Store는 별도 ALB(요청 분산)·EKS(컨테이너 운영)·RDS(DB) 구성으로 상품 조회와 모의 주문을 제공합니다.

## 09. 각 망의 설치용 인터넷을 먼저 확인합니다

인터넷으로 나가는 통신과 외부 사용자가 한국 API로 들어오는 통신은 각각 설정하고 시험해야 합니다.

| 대상 | 연결 계획 | 확인 방법·시점 |
| --- | --- | --- |
| M1·M2·M3 | 내부 VM → 자기 UTM → 자기 VyOS → 교실 게이트웨이 → 인터넷 | 10/20 교실망 정보와 두 PC의 VM 통신을 확인합니다. |
| M4·M5 | 내부 VM → 자기 UTM → 교실 게이트웨이 → 인터넷을 제안합니다. | 10/23까지 브리지 연결 허용 여부와 실제 통신을 확인합니다. |
| 설치·업데이트 | DNS는 도메인을 IP로 찾고, NTP는 장비 시간을 맞춥니다. 필요한 저장소에만 접속합니다. | 10/23까지 DNS 조회·실제 패키지 다운로드·시간 동기화를 확인합니다. |
| 팀원 간 연결 | 목적지로 가는 경로와 응답이 돌아오는 경로를 함께 설정합니다. | 10/28까지 내부·VPN 통신을 확인합니다. NAT(주소 변환)가 내부 통신을 방해하지 않도록 구분합니다. |
| 외부 고객의 API | 학교망 외부 진입 허용·공인 주소·요청 전달 설정·HTTPS 인증서가 필요합니다. | 10/23 가능 여부를 확인합니다. 불가하면 CDN 재생과 내부 API 시험을 구분해 기록합니다. |

같은 VMnet 번호를 사용해도 서로 다른 물리 PC의 VM이 자동 연결되지는 않습니다. IP·마스크·UTM 제품은 팀 기술서에 확정값을 기록합니다.

## 10. 보안 시험 5개 | 개선 전후 무엇이 달라지는가

시험용 계정·가짜 파일·시험 DB를 사용합니다. 출발지·계정·대상·시도 조건을 유지하여 개선 효과를 비교합니다.

| 담당·시나리오 | 개선 전 확인할 문제 | 개선 후 기대 결과 |
| --- | --- | --- |
| M1 · 1<br>직원의 관리 접속 | 본사 직원 PC에서 M2의 SSH 시험 서버에 불필요하게 접속할 수 있는지 확인합니다. | 직원 접속은 거부하고, 관리용 중계 서버(Bastion)를 통한 승인 관리자 접속은 유지합니다. |
| M2 · 2<br>반복 로그인 실패 | M2 시험 PC에서 SSH 로그인 실패를 반복해 로그 수집·경보·제한 상태를 확인합니다. | Wazuh 경보와 서버의 반복 시도 제한을 각각 확인합니다. 정상 관리자 로그인도 시험합니다. |
| M3 · 3<br>관리 API 노출 | M2 시험 PC가 Kubernetes 제어 노드의 관리 API에 연결할 수 있는지 확인합니다. | 승인된 관리 경로만 허용하고, 작업 권한도 제한합니다. 고객용 API는 정상 작동해야 합니다. |
| M4 · 4<br>백업 파일 권한 | 시험 계정이 백업 서버의 가짜 파일을 읽을 수 있는지 확인합니다. | 계정·파일 권한으로 비인가 읽기를 거부합니다. 승인된 백업·복원 작업은 유지합니다. |
| M5 · 5<br>직원의 DB 접근 | 캐나다 운영부서 시험 PC가 업무 VPN·본사를 거쳐 한국 시험 DB에 직접 연결하는지 확인합니다. | 직원의 직접 DB 접속은 거부하고 사내 포털·DNS와 승인된 앱·백업 접속은 유지합니다. |

포트 연결은 로그인 성공과 다르고, 경보는 차단과 다릅니다. 응답이 없으면 방화벽 기록과 왕복 경로를 확인하여 원인을 판단합니다.

## 11. 장애가 나도 복구할 수 있는지 확인합니다

복제는 변경 사항을 다른 DB로 전달하는 기능이고, 백업은 특정 시점의 사본을 보관하는 작업입니다.

| 영역 | 적용할 내용 | 확인할 결과 |
| --- | --- | --- |
| 서비스 실행 | Spring 앱을 개선 후 서로 다른 실행 노드에 2개 배치합니다. | 앱 하나 또는 실행 노드 하나를 중단하고 요청 성공 여부와 복구 시간을 기록합니다. |
| 진입 서버 | 개선 후 Nginx 2대와 공통 접속 주소 구성을 제안합니다. | 주 서버 중단 시 주소 인계와 API 요청을 확인합니다. 가상망 지원 여부를 먼저 시험합니다. |
| DB 복제 | M3의 운영 DB 변경을 M4 복제 DB에 전달합니다. | 11/05 첫 복제, 11/10 지연·단절 후 재개를 확인합니다. |
| 백업·실제 복원 | 10/30 최초 백업, 11/04 별도 DB 복원, 11/06 S3 사본 복원을 목표로 합니다. | 파일뿐 아니라 표본 데이터·건수·앱 조회 결과를 원본과 비교합니다. |
| 복구 목표·한계 | 10/23까지 허용할 데이터 손실 시간과 서비스 복구 목표 시간을 정합니다. | 11/09~10 최종 시험. PC·UTM·제어 노드·운영 DB의 단일 장애 가능성은 남습니다. |

백업 복원 시험에서 운영 DB를 덮어쓰지 않습니다. 캐나다 Store의 RDS 백업·복원은 별도로 확인합니다.
