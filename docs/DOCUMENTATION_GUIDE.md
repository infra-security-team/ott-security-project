## 기본 원칙
**개인 Notion 기술서가 최종 제출 문서의 원본입니다.** 다섯 명이 같은 목차로 설계·코드·설정·시험 결과를 기록합니다.
처음에는 사람마다 기술서 한 곳에서 시작합니다. 길어지면 기술별 하위 페이지로 나누고 상위 페이지에 목차를 둡니다.

## Notion과 GitHub를 함께 쓰는 이유
Notion에는 코드와 설명·결과를 함께, GitHub에는 실제 사용할 코드·설정 파일을 보관합니다.
GitHub의 단계별 설계·보안·시험 문서는 **핵심 결과와 Notion 상세 구간 링크**로 정리합니다. 개인 실습 기록 전체를 다시 쓰지 않습니다.
공통 구성도·통신표·실행 조건은 팀이 같이 사용하는 기준이므로 해당 GitHub 문서에서 합의하고 Notion에서 연결합니다.

## 작성할 때 필요한 최소 정보
문서 제목, 담당자, 수정 날짜, 관련 Issue를 먼저 적습니다. 검토 요청 시 검토자와 확인 결과를 남깁니다.
초보 팀원이 모든 문서에 여러 영어 상태와 별도 문서 ID를 중복 입력할 필요는 없습니다. 현재 작업 상태는 Issue에서 관리합니다.
문서에는 **계획인지 실제 적용인지, 실제 시험했는지**를 문장으로 분명히 씁니다. 기존 문서의 Draft는 초안, Approved는 합의된 문서, Implemented는 적용됨, Verified는 실제 시험 확인을 뜻합니다.

## 제출 전에 확인할 것
- 목적·담당 범위·실제 환경과 구성 그림이 있는가?
- 코드·설정·명령어에 목적·적용 위치·실행 결과가 있는가?
- 개선 전과 후를 같은 조건으로 비교했는가?
- 정상 서비스도 확인했는가?
- 원본 로그·화면·실제 판정과 남은 한계가 있는가?
- 문서의 코드와 GitHub 실제 파일이 일치하는가?
- 공동 결과와 개인 기여를 구분했는가?
- 비밀번호·키·실제 개인정보를 제거했는가?

## 최종 문서로 합치는 방법
1. 공통 개요와 전체 구성도·서비스 흐름·통신표를 앞에 둡니다.
2. M1~M5 개인 상세 기술서를 공통 목차에 맞춰 합칩니다.
3. 망 간 연결·앱·관제·복원·복구 등의 공동 시험을 별도 장으로 정리합니다.
4. 결론·한계·5인 기여·긴 코드 부록을 붙입니다.
5. 각 작성자가 자기 내용의 정확성을, PL이 기술 연결을, PM이 누락·형식·일정을 확인합니다.

권장 문서명: **OTT 인프라·보안 상세 설계 및 구현·검증 보고서**. 지정 양식은 없으며, 제출 형식·분량·필수 항목은 착수 때 강사에게 확인합니다.
