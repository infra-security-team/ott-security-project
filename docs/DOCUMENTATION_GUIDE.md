# StreamBridge 문서 작성 및 검토 표준 (v0.1)

> 적용 대상: M1~M5 전체 · 담당 PM: 유은혜 · 현재 상태: **팀 검토용**
>
> **문서의 목적은 작업을 많이 한 것처럼 보이는 것이 아니라 재현 가능하고 검증 가능한 증거를 남기는 것입니다.**

## 1. 문서 유형별 작성 기준

| 유형 | 답해야 할 질문 | 주요 산출물 | 관리 |

| 프로젝트 기획서/계획서 | 무엇을 왜, 누가 언제 할까? | 목표·범위·요구사항·기술 선택·일정·위험·완료 기준 | GitHub `docs/01-planning` |
| WBS | 어떤 작업이 언제 누구에 의해 끝나는가? | ID·담당·선행 작업·날짜·증빙·상태 | GitHub Issues/Projects; 표는 보조 |
| 회의록 | 무엇이 논의·확정·보류됐나? | 안건·결정·미결·담당·기한 | `docs/02-meetings` |
| 의사결정 로그 | 왜 이 기술과 구조를 택했나? | 대안·평가 기준·결론·제약·재검토 조건 | `docs/02-meetings/decision-log` |

## 2. 공통 메타데이터

모든 문서 첫머리에 아래 표 또는 속성을 둡니다.

| 필드 | 예시 |
|---|---|
| 문서 ID | `M5-NET-003` / `SEC-M3-002` |
| 제목 | 캐나다 지사 VPN 라우팅 구축 |
| 작성자 | M5 |
| 검토자 | PL 또는 인터페이스 담당 |
| 버전·날짜 | v0.1 · YYYY-MM-DD |
| 승인 상태 | Draft / Review / Approved / Archived |
| 구현 상태 | Planned / In progress / Implemented / Verified / Blocked |
| 관련 Issue | `#12` |
| 관련 Notion/코드 | 정확한 링크 |
| 변경 이력 | 변경일 · 변경 내용 · 이유 |

**승인 상태와 구현 상태를 분리**합니다. 계획서가 Approved여도 인프라가 Verified인 것은 아닙니다.

## 3. 파일/폴더 이름

- 날짜: `YYYY-MM-DD` (예: `2026-10-16-kickoff.md`)
- 파일 이름: 영문 소문자 + 하이픈 권장
- 실습 문서 ID: `M1-NET-001`, `M2-SEC-001`, `M3-SVC-001`, `M4-DR-001`, `M5-APP-001`
- 팀 공통 문서는 `COMMON-` 접두사 사용 가능
- 최신 합의 문서와 과거 버전은 구분; 기존 자료를 조용히 덮어쓰지 않기

## 4. 계획·확정·구축·검증 단계

1. **Proposed:** 의견이나 설계 대안이며 팀 합의 전.
2. **Approved:** 팀에서 구축 기준으로 합의한 설계.
3. **Implemented:** 실제 VM·서버·설정에 적용했으며 적용 로그가 있음.
4. **Verified:** 테스트 케이스와 결과·증빙이 확인됨.

실습 중인 취약한 AS-IS 구성은 격리된 랩에서만 생성합니다. 실제 공개 서비스 대상 공격 및 무단 스캔 금지.

## 5. 상세 기술서 작성 순서

[기술세부내역서 템플릿](templates/technical-detail-template.md) 복제 → Notion에 페이지 생성 → 담당자·Issue 링크 등록 → AS-IS 상태 기록 → 설정 및 명령어 **출력/이유** 기록 → TO-BE 변경 → 같은 테스트 조건으로 재검증 → 검토자 확인.

스위치/VyOS/VPN, Linux, MySQL, Kubernetes, Wazuh 등 **기술 하나당 문서 하나**를 권장합니다. 장비·설정이 다른 경우 테이블로 비교합니다.

### Notion 기술세부내역서

- 팀 Notion 페이지가 생성되면 **공식 링크를 여기에 등록**합니다.
- DB 공통 속성: 문서 ID / 제목 / 담당 / 영역(M1~M5) / 기술 카테고리 / 진행 상태 / 검토 상태 / 관련 Issue / 최종 수정일 / GitHub 설정 파일 URL.
- 공통 템플릿: `docs/templates/technical-detail-template.md`.
- GitHub에는 민감한 환경변수·비밀번호·VPN 사전공유키·실제 개인 IP·키를 올리지 않습니다.

## 6. 작성 품질 체크리스트

- [ ] 작업의 목적과 성공 기준이 구체적이다.
- [ ] OS/제품/버전 및 CPU·RAM·VM 환경이 기록되어 있다.
- [ ] IP, VLAN, 인터페이스, 포트, 방화벽 규칙과 출처가 있다.
- [ ] 명령어와 설정 선택의 **이유**가 적혀 있다.
- [ ] AS-IS 문제를 관찰했고 단순 가정과 실제 결과를 구별했다.
- [ ] TO-BE 변경 사항과 이전 구성 차이를 설명했다.
- [ ] 기대 결과뿐 아니라 **실제 결과/시간/화면/로그**가 있다.
- [ ] 미완료 항목과 한계, 단일 장애 지점이 적혀 있다.
- [ ] 담당자·검토자·관련 GitHub Issue 및 링크가 있다.
- [ ] 비밀정보·식별정보가 노출되지 않았다.

## 7. 팀 운영 권장 규칙

- 변경이 있으면 관련 Issue 갱신 → 기술서 수정 → 구성도 수정 → 테스트 증빙 추가.
- 운영 코드와 인프라 스크립트는 가능하면 브랜치/PR로 검토 후 `main`에 반영.
- GitHub에 코드와 원본 설정파일, Notion에 실행 과정/캡처를 두고 **서로 링크**합니다.
- 매주 PM은 `Blocked` 작업과 연쇄 의존 관계를 점검합니다.
