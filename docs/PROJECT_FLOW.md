# 프로젝트 흐름과 단계별 통과 기준
[처음 화면](../README.md) · [WBS](01-planning/wbs/README.md)

**시나리오 → 취약 환경 → 재현 → 개선안 → 개선 환경 → 재시험** 순서입니다. 실습 문서와 증거는 모든 단계에서 함께 작성합니다.

| 단계 | 수행 내용 | 다음 단계로 넘어가는 조건 | 저장 위치 |
|---|---|---|---|
| 1. 시나리오·설계 (W1) | 고객 문제, 출발지·대상·계정·입력·격리 범위·판정 기준 정의 | 담당·연동 담당이 시험 범위와 정상 업무 경로 확인, 공통 기준선 합의 | 보안 assessment, 아키텍처 network |
| 2. AS-IS 구축 (W2) | 계획한 취약 상태와 기본 OTT·통신 환경 구성 | 허용 통신·정상 기능·시험 환경 격리 확인 | architecture/as-is, infrastructure |
| 3. 재현·분석 (W2) | 승인된 시험을 수행하고 원인·영향 분석 | 원본 로그·설정·캡처로 실제 관찰 결과 확인 | security/assessment, Notion |
| 4. 개선안 (W3) | 원인에 맞는 정책·솔루션과 영향·되돌리기 설계 | 담당·연동 담당이 정상 서비스 영향과 적용 순서 검토 | security/remediation, architecture/to-be |
| 5. TO-BE 적용 (W3) | 정책·권한·관제·복구 대책 적용 | 적용 설정·변경 전후·기본 정상 기능 확인 | infrastructure, remediation |
| 6. 재시험 (W4) | 같은 출발지·대상·입력으로 반복 + 정상 기능 검사 | 전후 비교·탐지/차단·정상 기능·잔여 위험 교차 확인 | security/validation, testing |
| 7. 결과·발표 (W4) | 보안·APP·AI·복원 결과와 5인 기여 통합 | 미구현·미검증·제약 공개, 팀원별 설명·재현 가능 | reports |

개선 후 환경은 기존 랩을 변경하거나 별도 복제 환경으로 구성할 수 있습니다. **개선 전 설정·증거·복구 방법을 먼저 보존**하고, 비교 조건을 기록합니다. 다른 환경이면 비교에 영향을 주는 차이를 명시합니다.

## 병행할 수 있는 작업
각 망의 설계, 앱 개발, 기술 기록은 병행합니다. VPN·통합 배포·복원은 상대방의 준비가 필요합니다.
- M1 ↔ M3/M4/M5: 주소·VPN·필요 포트 합의 후 연결.
- M1 ↔ M2: Bastion·수집 경로 합의.
- M5 → M3: 실행 버전·API·DB 스키마·환경변수 목록 전달 → 공동 배포 시험.
- M3 ↔ M4: DB 버전·백업 조건 합의 → 격리 복원 → 앱 조회 대조.
- M2 ↔ 전원: 로그 수집 기준 제공 → 각자 연동 → 원본 로그·중앙 경보 대조.

## 판정에서 혼동하지 않기
포트 연결은 로그인 성공이나 데이터 탈취와 다릅니다. 탐지 경보는 차단 성공과 다릅니다. 타임아웃만으로 방화벽 차단을 단정하지 않습니다. 정상 서버 상태·경로·로그를 함께 확인합니다.
복제본 존재는 복원 성공이 아니며, Pod 복구는 전체 시스템 HA를 증명하지 않습니다.

필수 범위는 계획서 기준으로 유지합니다. 장비·시간 제약으로 바꿀 때는 영향과 대안을 기록하고 팀이 결정합니다. W4 신규 기능은 제한하고 마지막 2일은 결과 정리·발표에 확보합니다.
