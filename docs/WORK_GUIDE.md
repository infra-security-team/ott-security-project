# GitHub·Notion 작업 실행 가이드
[시작 안내](START_HERE.md) · [작성 예시](examples/README.md) · [폴더 지도](FOLDER_GUIDE.md)

## 1. 내 작업 찾기
README에서 자기 이름의 시작 Issue를 엽니다. 이후에는 Issues에서 `is:issue is:open "[M1]"`처럼 내 ID로 검색합니다. GitHub 계정이 연결되면 담당자(Assignee) 필터도 쓸 수 있습니다.
Issue는 작업 한 건, 체크리스트는 그 안의 실행 단계, WBS는 전체 순서입니다.

## 2. 체크와 상태의 책임
| 상태 | 누가 바꾸나 | 의미·다음 행동 |
|---|---|---|
| 할 일 | 담당자 | 아직 착수 전. 선행 조건 확인 |
| 진행 중 | 담당자 | 수행 중. 끝난 세부 항목만 체크 |
| 막힘 | 담당자 | 도움·선행 정보 필요. 원인·시도·필요한 도움 기록 |
| 검토 요청 | 담당자 | 완료 조건과 결과 링크 준비. 검토자 확인 대기 |
| 완료 | 담당자 또는 검토자 | 교차 검토 근거 기록 후 Issue를 Close as completed |

**상태는 Issue 본문의 ‘상태’ 한 곳에 씁니다.** 제목·WBS·별도 표에 매일 중복 갱신하지 않습니다. GitHub의 Open/Closed는 작업을 열고 닫는 구분이며 진행 중·막힘은 본문으로 구분합니다.

체크리스트를 채웠다고 즉시 완료는 아닙니다. 검토자는 설계/설정·증거·정상 기능·잔여 문제를 확인합니다. 보완이 필요하면 진행 중으로 되돌립니다. 재발한 문제는 Issue를 다시 열거나 후속 Issue로 연결합니다.
PM은 일정·의존성·막힘을 조율하고, 기술 검토는 해당 연동 담당자가 합니다. 여러 검토자가 있으면 해당 작업에 필요한 확인자를 Issue에 지정합니다.

## 3. Issue 작성·수정
- 기존 작업: Issue 본문 오른쪽 메뉴의 Edit → 상태·체크리스트·결과 링크 수정 → 저장.
- 댓글: 하단 입력란에 아래 결과 양식 작성 → Comment.
- 새 작업: Issues → New issue → **팀 작업** 또는 **보안 검증** 선택 → 빈칸 작성 → Create.
- 새 작업 제목: `[M1][W2] M1-02 본사 AS-IS 구축`. 본문에 WBS ID·담당·선행 작업 링크·기한·완료 조건을 반드시 씁니다.
- 편집 권한이 없으면 댓글로 변경 내용을 남기고 #6에 권한 확인을 요청합니다. PM이 대신 모든 작업을 작성하도록 두지 않습니다.
- 다음 단계 Issue는 전 단계 검토 때 담당자가 만듭니다. 이미 있다면 새로 만들지 않고 연결합니다.

## 4. GitHub에 파일 올리기
문서·설정 변경은 **브랜치 → Pull Request(PR, 변경 검토 요청) → 검토 후 병합**으로 남깁니다.

1. Code에서 저장할 폴더를 엽니다. 새 문서는 Add file → Create new file, 준비한 파일은 Upload files를 사용합니다. 기존 문서는 연필(Edit)로 수정합니다.
2. 파일명과 내용을 작성합니다. 템플릿은 미리보기 내용보다 **Raw의 Markdown 원문**을 복사하면 표·제목 형식을 유지하기 쉽습니다.
3. Commit changes에서 변경 이유를 쓰고 **새 브랜치 생성 및 PR 시작** 옵션을 선택합니다. 브랜치 예: `docs/m1-01-design`.
4. PR 본문에 관련 Issue를 `Refs #1`처럼 연결하고 무엇을 확인해 달라는지 적습니다. Issue 전체 완료 전에는 자동 종료용 `Closes #1`을 사용하지 않습니다.
5. 연동 담당자의 확인 후 병합합니다. 작성자가 병합한다면 검토 근거를 먼저 남깁니다.
6. 반영된 파일 링크와 PR/커밋 링크를 Issue에 등록합니다. 검토 중이면 PR 링크임을 표시합니다.

화면 명칭은 표시 언어·권한에 따라 다를 수 있습니다. 병합 권한이 없으면 권한이 있는 팀원에게 해당 PR 검토·병합을 요청합니다. 브랜치 보호 설정이 완료되었다는 뜻은 아니며, 여기서는 팀 운영 규칙을 정합니다.

## 5. Notion에는 실습하면서 작성
[기술세부내역서](templates/technical-detail-template.md)의 항목으로 페이지를 만듭니다. 문서 ID·담당·Issue URL을 먼저 적고, 환경 → 설정 이유·명령 → 실제 출력 → 문제 해결 → 시험 결과 순서로 기록합니다.
GitHub에는 재사용할 설정 원본과 최종 진단·시험 요약을 둡니다. Notion 전체를 GitHub에 다시 복사하지 않습니다.

## 6. 결과 댓글은 이 정도면 충분
```text
수행: 이번에 끝낸 작업
결과: 기대와 실제가 어떻게 일치/불일치했는지
산출물: GitHub 파일 또는 PR/커밋 URL
증거: Notion의 해당 시험 구간 URL (시각·출발지·대상·로그 포함)
남은 일/막힘: 없으면 없음, 있으면 필요한 도움
다음 행동: 다음 체크 항목 또는 다음 Issue
검토 요청: 확인할 사람과 항목
```
결과가 없으면 “미수행”, 실패하면 “실패”로 기록합니다. “구축 완료” 한 줄이나 파일 없는 폴더 링크만으로는 검토할 수 없습니다.

## 7. 막힐 때와 검토가 늦을 때
문제 재현·로그 확인·기본 점검을 한 뒤 진전이 없으면 그날 안에 Issue에 남깁니다. 하루 종일 혼자 기다리지 않습니다.
기술 문제는 연동 담당·PL, 일정·자원 충돌은 PM과 조율합니다. 검토 요청이 다음 작업일에도 확인되지 않으면 PM에게 일정 조율을 요청합니다. 주어진 권한 밖의 작업이나 미승인 시험으로 우회하지 않습니다.
