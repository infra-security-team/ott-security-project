# 작업하면서 쓰는 안내
[첫날 안내](START_HERE.md) · [개인 기술서 양식](templates/technical-detail-template.md)

## 1. 어디에 무엇을 쓰나요?
| 위치 | 적을 것 | 예 |
|---|---|---|
| Notion 개인 기술서 | 설계·코드·설정·이유·오류 해결·시험 결과 전체 | 백업 코드와 설명, 복원 화면, 데이터 비교 |
| GitHub 파일 | 실제 코드·설정 원본, 팀 공통 문서와 짧은 결과 요약 | backup.sh, 구성도, 시험 결과표 |
| Issue(작업 페이지) | 현재 상태·한 일·자료 링크·다음 행동 | 백업 완료 / 복원 예정 / Notion 링크 |

Notion 기술서 다섯 개를 모아 코드가 포함된 최종 상세 보고서를 만듭니다. 설명을 GitHub에 다시 전부 복사하지 않습니다.
실행 파일이 있다면 GitHub에 보관하고 Notion에도 해당 코드와 설명을 넣습니다. 코드가 바뀌면 문서 속 코드도 맞추고 파일 링크·확인 날짜를 남깁니다.
별도 파일이 없는 실습은 먼저 Notion 기록을 Issue에 연결합니다. 단계별로 요구된 구성도·시험 결과 요약은 해당 단계 검토 때 작성합니다. 이를 생략한다는 뜻은 아닙니다.

## 2. 본문과 댓글은 어떻게 다른가요?
- **본문:** 현재 담당·기한·상태·체크 항목·최신 결과 링크. 변경되면 수정합니다.
- **댓글:** 오늘 한 일, 질문, 문제와 해결 과정, 검토 의견. 과거 기록을 지우지 않습니다.

예시: 백업 파일만 만들었다면 생성 항목만 체크하고 상태는 진행 중입니다. 복원·데이터 비교·검토까지 끝나기 전에는 작업 전체를 닫지 않습니다.

| 상태 | 언제 사용하나요? |
|---|---|
| 할 일 | 아직 시작하지 않음 |
| 진행 중 | 작업하고 있으며 할 일이 남음 |
| 막힘 | 필요한 정보·환경·도움이 없어 다음 작업을 진행할 수 없음 |
| 검토 요청 | 완료 조건과 자료를 준비하고 다른 담당자의 확인을 기다림 |
| 완료 | 필요한 결과와 검토가 모두 끝남 |

상태는 Issue 본문 한 곳에 씁니다. Open은 열려 있음, Closed는 닫힘이라는 뜻입니다. 작업자가 체크하고, 해당 기술을 함께 쓰는 담당자가 검토합니다. PM이 모든 기술을 대신 승인하지 않습니다.

## 3. 하루를 마칠 때는 네 줄
```text
오늘 한 일:
자료 링크:
남은 일 / 필요한 도움:
다음 행동:
```

실패했다면 실패라고 적고 실제 오류·시도한 방법을 자료에 남깁니다. 결과가 없으면 미수행으로 둡니다.

<details>
<summary>Issue 본문 수정·댓글 작성 방법</summary>

Issue 본문 오른쪽 메뉴 → Edit → 상태·체크 항목·링크 수정 → 저장.
댓글은 하단 입력란에 작성 후 Comment.
권한이 없다면 댓글에 필요한 변경을 적고 PM에게 권한 확인을 요청합니다.
기존 후속 작업은 이미 만들어져 있습니다. [WBS](01-planning/wbs/README.md)에서 찾고 중복 생성하지 않습니다.
새로운 작업이 생긴 경우에만 New issue의 팀 작업 양식을 사용합니다.
</details>

<details>
<summary>실제 파일을 GitHub에 올릴 때 펼쳐 보세요</summary>

브랜치는 변경을 준비하는 별도 작업 공간, PR(Pull Request)은 그 변경을 팀에 검토받는 요청입니다.
## 4. GitHub에 파일 올리기
문서·설정 변경은 **브랜치 → Pull Request(PR, 변경 검토 요청) → 검토 후 병합**으로 남깁니다.

1. Code에서 저장할 폴더를 엽니다. 새 문서는 Add file → Create new file, 준비한 파일은 Upload files를 사용합니다. 기존 문서는 연필(Edit)로 수정합니다.
2. 파일명과 내용을 작성합니다. 템플릿은 미리보기 내용보다 **Raw의 Markdown 원문**을 복사하면 표·제목 형식을 유지하기 쉽습니다.
3. Commit changes에서 변경 이유를 쓰고 **새 브랜치 생성 및 PR 시작** 옵션을 선택합니다. 브랜치 예: `docs/m1-01-design`.
4. PR 본문에 관련 Issue를 `Refs #1`처럼 연결하고 무엇을 확인해 달라는지 적습니다. Issue 전체 완료 전에는 자동 종료용 `Closes #1`을 사용하지 않습니다.
5. 연동 담당자의 확인 후 병합합니다. 작성자가 병합한다면 검토 근거를 먼저 남깁니다.
6. 반영된 파일 링크와 PR/커밋 링크를 Issue에 등록합니다. 검토 중이면 PR 링크임을 표시합니다.

화면 명칭은 표시 언어·권한에 따라 다를 수 있습니다. 병합 권한이 없으면 권한이 있는 팀원에게 해당 PR 검토·병합을 요청합니다. 브랜치 보호 설정이 완료되었다는 뜻은 아니며, 여기서는 팀 운영 규칙을 정합니다.


</details>

## 4. 막히면 누구에게 물어보나요?
기술·연결 문제는 함께 작업하는 담당자나 PL에게, 일정·자원 충돌은 PM에게 알립니다.
“안 돼요” 대신 **하려던 일 / 실제 오류 / 시도한 것 / 필요한 도움**을 적습니다.
